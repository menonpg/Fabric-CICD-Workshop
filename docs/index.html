A plain-language guide to the GitHub Copilot + Microsoft Fabric CI/CD workshop · my notes as I follow along · updated Nov 4

The one-paragraph version

The workshop teaches two things. Part 1: how to work with GitHub Copilot (the AI assistant in VS Code) safely, on a tiny Python program that adds up sales by region. Part 2: how to release Microsoft Fabric work properly, using Git, reviewed changes and Dev → Test → Production stages. Part 1 is done (except one 10-minute drill); Part 2 is next, doing short labs called GH0 to GH9. Each lab asks Copilot to make one small change to the sales program, then checks it with tests.

What happened in GH4–GH7, in plain words

  • GH4: the "average per region" was wrong (it divided by 4 sales instead of 3 regions). First we wrote a test that fails on the bug, then fixed one line. Now it says 158.33 and 6 tests pass.
  • GH5: we gave Copilot the project's rules as files: .github/copilot-instructions.md (house rules), AGENTS.md, a read-only reviewer agent that can only read and search, a reusable "review my changes" prompt, and a small "skill" that explains the report.
  • GH6: we added --region East to show one region. An unknown region gives a clear error, not a crash.
  • GH7: we added a GitHub Actions workflow that runs the tests on every change (it passed on GitHub's servers). Then we wrote a GitHub issue describing the next change (input validation) and assigned it to Copilot. Copilot is now writing the code itself as a pull request; our job is to review it before merging.

How GH7 and GH9 finished

  • GH7: Copilot (working on GitHub, not on my laptop) wrote the input checks. Bad files now give a clear message such as "line 3: amount must be a number" instead of crashing. I reviewed it, all the cases in the lab's table worked, and I asked Copilot in a PR comment to add three missing tests, which it did. GitHub's test run passed, then I merged it.
  • GH9 (capstone): a sales file with only a header used to crash (divide by zero). Now it prints Average per region: 0.00. Done the "proper" way: a branch, a pull request (PR #3), an automatic test run on GitHub, then merge.
  • Final state: 23 tests pass; the normal report is unchanged (average 158.33).

GH8, the only one left (do it yourself, 10 min)

The point: practice telling an AI agent no, and checking it listened.

  1. In VS Code, create ws-part1-github-copilot/labs/starter/output/approval-demo.txt containing KEEP THIS PRACTICE TEXT.
  2. Open a new Copilot Agent chat. Tell it: "Use read-only checks first. Before overwriting anything, show the exact path and proposed change, then wait for my approval."
  3. Ask: "Propose replacing the content of that file with 'Replacement report'. Show the path and content, then stop and wait."
  4. When it asks, answer: "No. Keep the existing file unchanged." Deny any tool pop-up too.
  5. Open the file yourself. It should still say KEEP THIS PRACTICE TEXT.

Lesson: instructions guide the agent; only settings and permissions enforce. Always check the result yourself.

Day 2 talk: "The End of ClickOps in Microsoft Fabric" (plain words)

  • The problem ("ClickOps"): copying work from Dev to Test to Production by hand. People make mistakes, connections get hard-coded (so Test can still point at Dev's data), the environments drift apart, and recovery depends on the recycle bin.
  • The fix ("code-first"): Git is the single source of truth; each notebook or pipeline is saved as files; environments are created by code; each environment's settings are filled in automatically by a tool called fabric-cicd.
  • The three building blocks: workspaces (separate rooms for Dev, Test, Prod), item definitions (each item saved as files), and Git integration ("Update from Git" turns the files back into live items).
  • Infrastructure as Code: Terraform or Bicep creates the workspace, its capacity and a Key Vault for secrets, the same way for Dev, Test and Prod, instead of clicking in the portal three times. That's also why ordinary users often can't create workspaces themselves: they're meant to come from code.
  • Developer sandboxes: instead of everyone editing one shared Dev workspace, each developer "branches out" to their own feature branch and their own temporary workspace, works there, opens a pull request, and after the merge the shared Dev workspace updates from Git. The temporary workspace is then deleted.
  • The release flow: merge a pull request → an automated pipeline starts → Dev updates from Git → the tool deploys to Test → it stops and waits for a release manager's approval → then deploys the same thing to Production, with production settings swapped in.
  • Cleanup and cost: pause or shrink capacities when nothing is running; delete temporary environments and their credentials when done.
  • The closing message, three shifts: workspaces created by code (Terraform), not by hand · settings kept outside the code and filled in per environment (Variable Libraries) · releases run by an automated tool under a service account (fabric-cicd), not by people clicking. "Source of truth: Git. Execution: automated."

Tip: PR checks stuck on "Queued: waiting to run"

When Copilot's cloud agent writes a pull request, GitHub holds its test runs until a person approves them, so the checks sit in "Queued" forever. To unstick: click "Approve and run workflows" on the PR, or open the Actions tab, open the waiting run and click Re-run jobs. Then click Ready for review (draft PRs can't be merged). It's a built-in guardrail: AI-written code can't even run CI until a human says so.
